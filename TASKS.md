- [ ] **`copy.deepcopy` of an array item SHARES its attribute values** @low — `NDArrayItem` has no `__deepcopy__`, so numpy's copies the array and `__array_finalize__` hands over the attrs BY REFERENCE. Reproduction: `a = Spectrogram(np.zeros((2, 2)), params={"fft_size": 64}); b = copy.deepcopy(a); b.params["fft_size"] = 128` → `a.params["fft_size"] == 128` (measured 2026-09-27; the same holds for `GridMask.params`). It matters because the flow engine's fan-out gives each branch a `deepcopy` of the step result (`recordstream/flow/execute.py:162`), so two branches share one `params` dict. It is LATENT today: no op in recordstream, waivefront or annotaide edits an item's `params` in place (grep 2026-09-27). The likely fix is a `__deepcopy__` on `NDArrayItem` that deep-copies the `_item_attrs` values (next to the pickle `__reduce__`/`__setstate__` added 2026-09-27), pinned by a fan-out test where one branch edits `params`. Found while fixing the pickle defect; deferred by user decision. @2026-09-27

- [ ] **Decide whether `PredictionsSink` collapses into `DataSink`** @medium @refactor — since 2026-07-29 this package carries TWO sink protocols: `storage.base.DataSink.write(record)` (adapted into op chains by `RecordSinkOp`) and `predictions.PredictionsSink.write(prediction, metadata)`. The split is real — a model emits a BATCH while the sink contract is per-record, so the prediction and its record's metadata arrive separately — and it is load-bearing downstream, where a visual editor's node palette keys off the signature difference. The alternative: have the consuming runnable build the record (it already holds both halves — it slices the batch per record before calling `write`) and write through the ordinary `DataSink`, deleting `PredictionsSink` and letting prediction sinks become ordinary `category="sink"` canvas nodes. That touches the predict path of every consuming runnable, which is why it was NOT bundled into the move. Decide deliberately; do not let the two protocols blur by drift.
